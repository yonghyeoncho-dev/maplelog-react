# maplelog-react

실운영 중인 메이플스토리 팬 서비스 **[maplelog.gg](https://maplelog.gg)** 를 React + TypeScript로 리빌드하는 프로젝트입니다.

## 원본 서비스 (maplelog.gg)

- 메이플랜드 유저를 위한 비공식 팬 서비스 — 1인 기획·개발·운영
- 실아이템 스탯 DB · 인게임 확률을 재현한 강화 시뮬레이터 · 공대 정산 원장 · 혼테일 타이머
- Vanilla JS SPA (프레임워크 없이 라우팅·상태·렌더링 직접 구현)
- Firebase (Firestore · Cloud Functions · Hosting), Discord OAuth

## 리빌드 목표

원본에서 원리 수준으로 직접 구현했던 것들을 모던 스택으로 다시 세우며, 두 구현의 차이를 커밋 히스토리로 기록합니다.

- [x] Vite + React + TypeScript 프로젝트 셋업
- [x] 아이템 DB 조회 화면 — 이름 검색 · 부위 · 직업 필터
- [x] 상세 화면 + 라우팅 (`/` 목록, `/item/:code` 상세)
- [x] 실 데이터 연동 및 데이터 페칭 구조화
- [ ] 강화 시뮬레이터 컴포넌트 분리 설계
- [ ] 독립 URL 배포 (Firebase Hosting)

## 화면 구성

| 경로 | 화면 | 비고 |
|---|---|---|
| `/` | 아이템 목록 | 한글·영문 검색, 부위·직업 필터. 검색 조건은 쿼리스트링에 보존 |
| `/item/:code` | 아이템 상세 | 착용 조건 · 옵션 · 기타로 나눈 스탯 표 |

## 데이터

`public/items.json` — 실제 장비 아이템 **245종**입니다.
원본 서비스는 이보다 훨씬 많은 아이템을 다루지만, 이 저장소는 화면 구현을 보이는 것이
목적이므로 부위 38종이 모두 들어가도록 레벨 구간을 고르게 추린 부분집합만 포함했습니다.

원본 데이터는 `[코드, 한글명, 영문명, 레벨, 스탯객체]` 형태의 배열이고, 이 저장소에서는
화면에서 다루기 좋도록 객체로 펼치고 착용 조건과 옵션을 분리했습니다.

부위는 아이템 코드 앞 3자리로 판정합니다 (100 모자, 107 신발, 140 두손검 …).
같은 이름의 아이템이 코드만 다르게 여러 개 존재하므로(예: `호검` 4종),
목록의 `key`와 상세 라우트는 이름이 아니라 코드를 씁니다.

### 왜 import가 아니라 fetch인가

원본 규모의 데이터는 `import`하면 번들에 통째로 들어가 첫 화면이 뜨기 전에 전부 받아야 합니다.
`public/`에 두고 fetch하면 화면 뼈대를 먼저 그리고 데이터는 뒤따라오게 할 수 있습니다.
데이터가 늘어나도 구조를 바꾸지 않아도 되도록 처음부터 이렇게 잡았습니다.

목록과 상세를 오갈 때 매번 다시 받지 않도록 모듈 스코프에 캐시를 두었고,
두 화면이 동시에 요청해도 네트워크 요청은 한 번만 나가도록 진행 중인 Promise를 공유합니다.

## 원본과의 구현 차이 기록

| 원본 maplelog (Vanilla) | 이 저장소 (React) |
|---|---|
| `location.hash` 파싱 후 렌더 함수 직접 호출 | React Router의 경로 선언 매칭 |
| `location.search` 직접 파싱 + `history.pushState` 직접 호출 | `useSearchParams` |
| 상태 변경 후 렌더 함수 수동 호출 | `useState` — 값 변경이 곧 렌더 |
| 문자열 조립 후 `innerHTML` 주입 | JSX 리턴, DOM 반영은 React 담당 |

## 리빌드 중 만난 문제

**상세로 갔다 돌아오면 검색어가 사라졌다.**
목록 컴포넌트가 화면에서 사라질 때 그 안의 상태도 함께 사라지는 것이 원인이었습니다.
검색 조건은 화면이 잠시 들고 있을 값이 아니라 그 화면이 무엇을 보여주는지를 규정하는 값이라고
판단해, 상태를 컴포넌트에서 URL 쿼리스트링으로 옮겼습니다. 새로고침과 링크 공유도 함께 해결되었습니다.

**한글로 검색하니 "장갑"이 "ㅈ자장ㄱ가갑"으로 입력됐다.**
React Router의 주소 변경이 지연 렌더링으로 처리되면서, 한글 조합 도중에 이전 값이 입력창에
다시 써지고 브라우저가 조합을 강제 종료하는 것이 원인이었습니다. 입력창이 보여줄 값은
컴포넌트가 동기적으로 들고, URL 반영은 `compositionend` 이후로 미루도록 고쳤습니다.
영어로만 테스트했으면 발견하지 못했을 문제라, 이후로는 한글 입력을 확인 항목에 넣고 있습니다.

**전체 데이터로 붙여보니 입력이 밀렸다.**
카드 하나당 DOM이 10개 남짓이라 수천 종을 한 번에 그리면 수만 개가 쌓이고,
검색어를 한 글자 칠 때마다 그걸 다시 그렸습니다.
렌더 상한(60개)과 "더 보기"를 두고, 필터 계산은 `useMemo`로 조건이 바뀔 때만 하도록 했습니다.
